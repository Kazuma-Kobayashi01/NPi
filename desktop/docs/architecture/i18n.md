# UI language (i18n)

Code: `app/i18n.js` (`window.OMP_I18N`), the dictionaries `app/i18n/{ui,settings,settings-desc}.js`, the `language` tweak, the Language row in Settings → General (`app/settings-schema.js`). Test: `test-i18n.mjs`.

## Languages and the setting

`zh-CN`, `zh-TW`, `en-US`, `ja-JP`. The tweak `language` is `auto` (default) or one of them. `OMP_I18N.resolve` maps it to a supported locale; `auto` follows `navigator.languages[0]` (`zh-TW/HK/MO/Hant*` → zh-TW, other `zh*` → zh-CN, `ja*` → ja-JP, everything else en-US). `app-live.jsx` calls `setLocale(resolve(t.language))` on every render, so a change in Settings re-renders the window at once; `setLocale` also sets `<html lang>`. The Language row is a full-width segmented control that writes each language in its own name, plus Auto.

It changes this interface only. The model's reply language, system prompts, tool output and file names are untouched; the Settings row says so.

## `t(key, vars)`

Selected locale → en-US → the key itself, then `{name}` filled from `vars` (an unknown variable stays as written). There is no plural machinery: write strings that read well for any number ("Tools used: {n}").

A key is either **the English source text**, which is then its own en-US entry (so the English UI is exactly what the components always said, and an untranslated string degrades to English), or a **dotted id** (`work.thought`) whose English text is registered with `addEn`. Use a dotted id when the English text is not the natural key.

Components call it through a file-local alias (`_PSB_T`, `_CS_T`, …): the Babel scripts share one top-level scope and `t` is already the tweaks object in `app-live.jsx` and the Settings page.

## Dictionaries

One row per key: `[English, zh-CN, zh-TW, ja-JP]`, registered with `I.add([...])`. One row per key keeps the three translated sets identical by construction; `test-i18n.mjs` still checks identical keys, no empty value, the same `{placeholders}` as the key in every language, that each dotted id has an English text, and that **every text in the Settings schema (title, blurb, group name, label, description, option label) has a translation**: a new Settings row needs its entries in `settings.js` / `settings-desc.js` or that test fails.

|File|Holds|
|---|---|
|`i18n/ui.js`|mode switch, sidebars, window chrome, start page, composer, SideChat / Academic Copilot pane, the thinking-and-tools box (`work.*`), the subagent setup form|
|`i18n/office.js`|the Office window and the tab's Office switch (phase, capability and PR status ids `phase.*`, `cap.*`, `pr.*`)|
|`i18n/settings.js`|Settings page chrome, section titles/blurbs, group names, row labels, option labels, interface-detail steps|
|`i18n/settings-desc.js`|row descriptions (keyed by the schema's exact text, `backtick` code tokens left untranslated)|

Terms: conversation 会话/對話/会話, project 项目/專案/プロジェクト, agent 代理/代理/エージェント, subagent 子代理/子代理/サブエージェント, tool 工具/工具/ツール. zh-TW uses Taiwan vocabulary (專案, 設定檔, 外掛, 儲存), not a character conversion of zh-CN.

## Where it is applied

- Settings: `SettingsRow` translates the label and description it is given (so custom rows that pass the schema's English text are covered), `SettingsSeg` its option labels, `SettingsStrip`, the page header, search, footer and reset buttons. Search (`OMP_SETTINGS.search`) matches the English text and the text of the current language.
- `app/greetings.js` has natural greetings per language (`greeting({ locale })`; the name goes last after a comma so it can drop out, ja adds さん).
- `app/work-box.js` builds its lines through `t` (a bare context such as a test gets the ids back).

## Not translated (still English)

Custom Settings rows' own inner text (account, models, vendors, usage, MCP/skills, approvals, conversations manager, shortcuts editor, computer-use, widgets, notifications row controls, wallpaper names), approval-mode names and the model/thinking menus, slash-command descriptions and the command palette, tool cards and tool names, ask/approval dialogs other than the subagent setup form, the conversation tree, git browser, file preview, terminal/browser panels, error and toast messages from `live.js`, dates in the chat sidebar (`en-US` format), and everything omp or the Rust side sends. Add them as the surrounding code is touched: wrap the literal in the file's alias and add a row.
